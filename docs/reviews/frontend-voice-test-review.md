+**Statische Prüfung der bereitgestellten Quelldaten; keine Laufzeitprüfung.** `docs/qa-check-lock.md` hält PRD10 QA exklusiv für Prüfungen gesperrt. Ich habe weder Server noch Browser oder Live-Audio gestartet. Die Zeilennummern waren in den eingefügten Quelldaten nicht enthalten; ich nenne deshalb die Funktionsanker.

- **Befund – Folgeauftrag direkt nach `working → idle` wird abgewiesen:** In `src/App.tsx`, `handleEvent` beim `status`-Event, wird `taskDispatchRef.current` synchron aktualisiert. `submitTask` prüft zusätzlich `status.state === 'working'`, wobei `status` aus dem letzten React-Render stammt. Kommt nach einem `idle`-Event ein finales Sprachtranskript vor dem nächsten Render, ist der Ref bereits frei, aber die Callback-Closure kann weiterhin `working` sehen. Sie weist den Auftrag ab und zeigt „another task is still running“. **Reproduktion:** während eines Tasks erst `status(state: idle)` und unmittelbar danach ein finales User-Transkript mit neuem ID zustellen. **Auswirkung:** gültiger Folgeauftrag geht verloren. **Minimaler Fix:** für die synchrone Sperre den Ref als maßgebliche Quelle verwenden oder den Status ebenfalls synchron in einem Ref aktualisieren.

- **Befund – ID-Deduplizierung ist auf 200 Einträge begrenzt:** In `src/App.tsx`, beim finalen User-Transkript, wird die älteste ID aus `handledVoiceTranscriptIdsRef` entfernt, sobald die Menge über 200 Einträge wächst. Wird danach eine alte ID erneut geliefert, gilt sie nicht mehr als behandelt und kann einen zweiten Task starten. **Reproduktion:** mehr als 200 verschiedene finale User-IDs zustellen, eine abgeschlossene alte ID erneut zustellen. **Auswirkung:** „eine stabile ID startet genau einen Task“ gilt nur innerhalb des begrenzten Cache-Fensters. **Minimaler Fix:** behandelte IDs mindestens so lange wie die WebSocket-Session vollständig halten oder eine andere langlebige Deduplizierung einsetzen.

Weitere Prüfpunkte aus dem sichtbaren Code:

- **Interims:** Der Task-Pfad ist an `event.final` gebunden; Interim-Transkripte starten in diesem Handler keinen Task.
- **Fehlende ID:** Der Client zeigt bei finalem User-Transkript ohne String-ID eine sichtbare Fehlermeldung. `AssistantSession.emit` ergänzt bei finalen User-Transkripten ohne ID allerdings eine UUID; der Clientfehler ist damit ein Fallback für fehlerhafte oder abweichende Serverereignisse.
- **Profilübermittlung:** `submitTask` baut den Task-Payload aus `text` und `profile: projected`; bei erkannter Kategorie kommt `projected` aus `profileFor`, das `neededProfileFor` aufruft. Bei nicht erkannter Kategorie wird `emptyProfile` gesendet. Der Server projiziert erneut mit `neededProfileFor`. Im sichtbaren Transkriptpfad ist kein Aufruf von `confirmBooking` zu sehen; gesprochenes „yes/confirm“ löst dort keine Freigabe aus.
- **Freigabe:** `confirmBooking` verlangt Approval, gesetzte Checkbox, nicht abgelaufene Freigabe, unverbrauchtes Token und passende Version. `AssistantSession.confirm` prüft zusätzlich Version, aktuellen Kontext und Profilprojektion. Das tatsächliche Token- und Ablaufverhalten von `ApprovalGate` konnte ich ohne dessen Quelltext nicht vollständig beurteilen.
- **Stop:** `AssistantSession.stop` erhöht Version und invalidiert Gate/Binding, leert aber `offers`, `currentKind` und `currentProfile` nicht; `select` prüft Offer-ID und übermittelte Version. Die normale UI verwirft alte Karten über Versionsprüfungen. Der Server-Handler selbst könnte nach `stop` jedoch eine alte Offer-ID mit der nun aktuellen Version akzeptieren. Minimaler Fix wäre, beim Stop auch die gespeicherten Offers und den aktuellen Kontext zu löschen.
- **Audio interrupted:** `App.tsx` ruft für `interrupted` `audio.clearPlayback()` auf und meldet, dass das Mikrofon an bleibt. `src/hooks/useAudio.ts` war im bereitgestellten Ausschnitt nicht enthalten; die tatsächliche Trennung von Playback und Mikrofon konnte ich daher nicht verifizieren.
